# Synthetic Data — Northstar Finance OS

All CSVs in this folder are generated by `generate_data.py` — **entirely synthetic**, fictional data for the fictional Northstar Health Group. No real customer, vendor, employer, or financial data is used anywhere in this project (see AGENTS.md's no-real-data rule).

## Run it

```bash
python 04-data/generate_data.py
```

Deterministic: the script sets a fixed random seed (42), so re-running it reproduces byte-identical CSVs. There's nothing to configure — it writes straight into this folder.

## What this represents

These CSVs are the **raw, pre-ingestion** extracts that would arrive from each source in [system-architecture.md](../03-architecture/system-architecture.md) — Billing (AR invoices), AP (vendor invoices, arriving as email/PDF per [discovery-notes.md](../01-discovery/discovery-notes.md)), Banking (bank statement export), and the intercompany spreadsheet. They are **not** yet in the clean, validated shape of the target [data-model.md](../03-architecture/data-model.md) — that transformation is exactly what the Phase 9 ingestion pipeline (`06-python/`) is built to do. So a few fields here won't look like the final schema:

- `invoices.vendor_name_raw` — the AP vendor name as it arrived (sometimes inconsistent), separate from the canonical `vendors.vendor_name`; `vendor_code` is left blank whenever the raw name doesn't cleanly match, standing in for the fuzzy-matching problem the ingestion pipeline needs to solve
- Everything is joined by natural business keys (`entity_code`, `customer_code`, `vendor_code`, `account_code`) rather than the surrogate `entity_id` / `customer_id` foreign keys in the final data model — that resolution also happens at ingestion

Scale note: this is a deliberately readable subset — a few hundred rows total across three close periods (June–August 2026) — not a literal reproduction of the ~5,000 transactions/month figure in AGENTS.md's fictional client profile. The point is realistic messiness at a size a reviewer can actually open and read, not raw volume.

## Planted data-quality issues

Every issue PLAN.md §19 calls for is deliberately injected, and logged as it's created to **[data-quality-log.md](./data-quality-log.md)** — regenerated fresh each run. That file is the ground truth: Phase 9 (ingestion/validation) and Phase 13 (reconciliation) should be checked against it, not just eyeballed for "looks about right."

Categories injected: duplicate invoices, duplicate payments, missing entity codes, inconsistent vendor names, incorrect account mappings, missing invoice references (unapplied cash), unmatched bank transactions, unmatched intercompany transactions, late transactions (entry dated in the prior month but tagged to the current close period). Both GBP and USD appear throughout, driven by each entity's functional currency.

## What's deliberately *not* injected

Journal entries always balance (debit = credit) and no journal is ever self-approved (`created_by` ≠ `approved_by` whenever a journal is posted) — these are the two hard constraints from [data-model.md](../03-architecture/data-model.md), enforced even in intentionally messy source data, because they represent system-level guarantees the target architecture makes, not data-quality problems for the pipeline to catch.
