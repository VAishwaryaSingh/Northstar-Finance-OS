# AGENTS.md — Context for AI Coding Tools

Read this and `PLAN.md` fully before making any changes. `PLAN.md` is the canonical specification; this file is the working-context summary for AI coding tools.

## Project purpose

Northstar Finance OS is a portfolio proof-of-concept demonstrating end-to-end finance-transformation and AI-native ERP capability: process discovery, requirements, target architecture, a relational data model, SQL, a Python ETL/reconciliation pipeline, a REST API, an AI-assisted accounting workflow with human-in-the-loop controls, an implementation/migration plan, and a solutions-consulting demo.

It exists to show capability, not to claim experience the candidate doesn't have. See PLAN.md §1–§2 for full positioning.

## Fictional client

**Northstar Health Group** — a fictional UK/US healthcare group, three entities (Northstar Health Holdings Ltd (UK), Northstar Health Services Inc (US), Northstar Shared Services Ltd (UK)), GBP/USD, ~5,000 transactions/month. Always state clearly that this is fictional. Never use real customer, employer, or personal financial data (PLAN.md §4, §19, §32).

## Architecture (target state)

Sources (billing, bank, AP, legacy ERP) → Integration/ingestion layer → Validation & normalisation → Finance data model → Deterministic accounting rules + AI assistance → Human approval → Journal/subledger posting → Automated reconciliation → Close Control Centre → CFO reporting. Full diagram in PLAN.md §17.

**Rule: AI assists accounting decisions; it never bypasses accounting controls.**

## Coding conventions

- Python: pandas, SQLAlchemy, Pydantic where appropriate, pytest. Avoid unnecessary frameworks.
- API: FastAPI unless there's a strong reason otherwise.
- Database: PostgreSQL preferred; SQLite acceptable for a first iteration.
- Code should be readable by a finance professional learning engineering concepts — prefer clarity over cleverness.
- Prefer small, testable, incremental changes. Do not rewrite the whole repo without a specific reason.

## Accounting assumptions

- Journal entries must always balance: Total Debits = Total Credits.
- Every transaction carries: entity, date, currency, source, accounting classification, status.
- Deterministic rules handle accounting controls; AI handles ambiguous classification/explanation/exception-handling only (PLAN.md §23, §25).

## Testing requirements

Every meaningful component needs tests: duplicate detection, currency conversion, mapping, reconciliation (Python); valid/invalid requests, duplicate posting, error responses (API); debit=credit, approval-required, required-fields (accounting); high/low-confidence, ambiguous, missing-data, adversarial cases (AI). See PLAN.md §30–§31.

## Security rules

- No real API keys, passwords, customer data, employer-confidential data, or personal financial information — ever.
- Use `.env.example` with placeholders only.
- Document auth, authorisation, secrets management, least privilege, audit logging (PLAN.md §32). This is a portfolio POC, not a production-secure ERP — state limitations explicitly.

## No-real-data rule

All data is synthetic, generated by `04-data/generate_data.py`, and intentionally messy (duplicates, missing fields, unmatched transactions — PLAN.md §19). Never substitute real data of any kind.

## Documentation requirements

Every phase needs: the deliverable itself, evidence it runs/was reviewed, tests where applicable, documented assumptions, documented limitations, a git commit, and the candidate must be able to explain it unaided (PLAN.md §39).

## Definition of done (per phase)

1. Code/document exists.
2. It runs or can be reviewed.
3. It is tested where applicable.
4. README/documentation explains it.
5. Assumptions are documented.
6. Limitations are documented.
7. Git commit is made.
8. The candidate can explain it without the AI tool.

## Workflow for every task

1. Inspect the relevant existing files first.
2. Propose a plan before large changes.
3. Implement incrementally.
4. Run tests.
5. Inspect outputs.
6. Update documentation (including the `STATUS` block).
7. Commit the change with a descriptive message (`feat:`, `fix:`, `docs:`, `test:` — never `update`/`stuff`/`final`).
8. Record major decisions as an ADR under `ADRs/` when the decision is significant (see PLAN.md §37 for examples and format).
