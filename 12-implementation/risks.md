# Risk Register — Northstar Finance OS Implementation

Risk concentrates in Implementation Plan Phases 6-8 ([implementation-plan.md](./implementation-plan.md)) — Phases 0-5 (discovery through testing) carry low risk by design, since nothing in them is live or irreversible. Likelihood/Impact are Low/Medium/High, consistent with how a real engagement would present this to a steering committee, not a numeric score this project has no basis to calibrate precisely.

| # | Risk | Category | Likelihood | Impact | Mitigation | Owner |
|---|---|---|---|---|---|---|
| R1 | Legacy vendor/customer names don't fuzzy-match cleanly, leaving more unmapped master data than this project's synthetic dataset (2 known variants) suggests | Data migration | Medium | Medium | [06-python/mappings.py](../06-python/mappings.py)'s cutoff (0.75) and matching approach need re-tuning against real legacy data before go-live, not assumed to transfer as-is; unmapped records route to a manual review queue, never silently dropped | Shared Services Manager |
| R2 | Opening balances don't tie to the legacy system's own closing trial balance | Data migration | Medium | High | [Validation](./migration-plan.md#validation)'s balance/control-total checks are a hard go/no-go gate per entity, not a post-migration nice-to-have | Group Financial Controller |
| R3 | The 10,000 approval threshold ([journal_workflow.py](../08-accounting-automation/journal_workflow.py)) is still a documented assumption, not a confirmed policy, and goes live with the wrong figure | Control design | Medium | Medium | Confirmed explicitly in Implementation Plan Phase 4 (Configuration), before any entity's pilot, not discovered live | CFO |
| R4 | A control that should be structurally impossible (unbalanced journal, self-approval) turns out not to be, once real data/real users exercise paths this project's synthetic tests didn't anticipate | Control design | Low | High | [schema.sql](../05-sql/schema.sql)'s constraints are enforced by the database itself, not just application logic — see that file's tests, which include deliberately trying to break both rules. Real UAT (Implementation Plan Phase 5) specifically re-runs those same deliberate-break attempts against production-like data before go-live | Group Financial Controller |
| R5 | AI-assisted classification ([09-ai/](../09-ai/)) produces a confident-looking wrong suggestion that isn't caught by the amount-outlier check or audit sampling — see [09-ai/evaluation.md](../09-ai/evaluation.md)'s own documented ~9-10% inappropriate-automation rate on its evaluation set | AI / control design | Medium | Medium | Audit sample rate ([should_sample_for_audit](../08-accounting-automation/exception_rules.py)) is a tunable, documented assumption (5%) — raise it for higher-risk vendor/amount combinations rather than treat the residual risk as zero; this is a known, accepted limitation, not a defect to eliminate before go-live | CFO |
| R6 | Two systems running in parallel during a per-entity cutover diverge, and no one notices before the legacy system for that entity is retired | Migration / cutover | Medium | High | [Rollout Plan](./rollout-plan.md)'s parallel-run requirement is a hard gate (one full close cycle, validated both ways) before any legacy system is retired, not a target best-effort | Shared Services Manager |

| R9 | Real vendor invoice amount patterns are tighter than this project's synthetic (uniformly random) data, making [check_amount_outlier](../08-accounting-automation/invoice_classification.py) either too noisy (real deployment) or — the opposite risk not yet seen in testing — too loose to catch a genuine anomaly against a vendor with naturally wide-ranging real invoice amounts | Control design | Low | Low | Threshold (3 standard deviations, [invoice_classification.py](../08-accounting-automation/invoice_classification.py)) explicitly documented as untuned against real data — Implementation Plan Phase 5 (Testing) re-validates it against a sample of real historical vendor invoices before go-live, not left at its synthetic-data default | Group Financial Controller |
| R10 | FX conversion logic, exercised for the first time at scale when the US entity rolls out last, has an edge case the two GBP-only entities' pilot never exercised | Technical | Medium | Medium | [Rollout Plan](./rollout-plan.md) deliberately sequences the US entity last and calls out re-verifying `requires_fx_conversion` specifically at that stage, rather than assuming what worked for GBP-only entities generalises | Group Financial Controller |
